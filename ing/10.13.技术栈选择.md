## 1. SwiftPM 是什么

Swift 官方包管理 + 构建系统。一个包 = `Package.swift`(清单, 相当于 pyproject.toml) + `Sources/` + `Tests/`, 三个命令 `swift build` / `swift test` / `swift run`。对应 Python 世界就是 pip + venv + setuptools + pytest 的角色合体。

关键特性: 它只产"库"和"命令行程序", **不产 iOS app** (app 要 .app 包、Info.plist、签名, 那是 xcodebuild 的活)。所以架构是: dog 解析/树模型做成 SwiftPM 包 (DogKit), 全程 `swift test` 无头开发; app 只是薄壳, 引用这个包。

类比你的项目: 相当于把 `f2_dog_io` 那层纯逻辑抽成独立可 pytest 的包, Qt UI 单独一层。

## 2. golden JSON 是什么

"基准文件测试" (golden/snapshot test): 拿一个已知正确的实现产出标准答案存成文件, 以后每次改动都跟标准答案对拍。

具体做法: 用 macOS 的 Python 解析器把 `__dog格式__/样例` 逐文件解析成 JSON (整棵树 + 每个节点的 前缀/正文/尾缀 字段), 存为 golden 文件; Swift 的 DogKit 解析同一文件, 输出同形状的 JSON, 两个 JSON 逐字段比对 —— 不一致就是移植出了 bug。

JSON 在这里只是"测试中间产物"的磁盘写法 (约等于 Python dict 的文本形式), **不是 dog 的第二种官方格式**, 不进产品、不给用户看。

## 3. 在 OS 26 的机器上开发合适吗

是, 更合适。原因:

- iOS 开发只能在 macOS 上做, 且每个 Xcode 版本有最低 macOS 要求 —— 新 Xcode 装不进老系统。这台机器是 macOS 15.6 (Darwin 24.6), 能否装到最新 Xcode 取决于 Apple 的要求, 有不确定性
- Apple 会不定期强制"上架提交必须用较新 SDK 构建", 所以迟早要追新 Xcode; 直接在有 OS 26 的机器上开发, 绕开所有版本纠缠
- **不影响 app 的最低支持版本**: 用新 Xcode 编出的 app 照样可以只要求 iOS 17+ (那是 deployment target 决定的); 想在模拟器里测旧系统, 下载旧 iOS runtime 即可
- 如果那台是 Apple Silicon 且内存 ≥16G 就更理想

结论: 起步开发在哪台都行 (只要能装到够新的 Xcode), 但上架阶段大概率要用新机器 —— 不如一开始就放 OS 26 那台。换机器对协作无影响, 在新机器上开 Claude Code 即可。

## 4. BSP 和 app target 是什么

- **target**: Xcode 工程里"一个产出物"的配置单元。一个工程可以有多个: app target (编译出 .app 本体)、测试 target 等。我们的工程 = 一个 app target (薄 UI 壳) + 本地包 DogKit (逻辑)
- **BSP (Build Server Protocol)**: 一个协议, 让编辑器 (VSCode 的 Swift 插件) 能问构建系统"这个文件属于哪个 target、用什么编译参数", 如此补全和跳转才准确。类比: Pylance 得知道解释器和包路径才能解析 import, Swift 插件对 Xcode 工程同理。对 SwiftPM 包这些信息本来就现成; 对 .xcodeproj 工程, Xcode 16 起 xcodebuild 内置了 BSP 服务, 所以 VSCode 里 app target 的代码也能正确索引

一句话: BSP = VSCode 插件和 Xcode 工程之间的桥。

## 6. 这几个术语 (附 Qt 对照)

- **SwiftUI**: 苹果的声明式 UI 框架 ≈ QML。描述"界面长什么样、跟着状态自动变", 不手写 setText/repaint
- **行列表**: `List` = 系统标准列表 (自带滚动/样式, ≈ QListView); `LazyVStack` = 自己拼的滚动列 (≈ QScrollArea + QVBoxLayout)。我们的树折叠之后渲染出来的就是"可见行数组", 对控件来说就是个平铺列表
- **TextField**: 输入框 ≈ QLineEdit; iOS 16+ 的 `TextField(axis: .vertical)` 能自动换行长高 ≈ 轻量版 QTextEdit。用于"点开节点后编辑它"
- **TextKit**: 苹果的文本排版引擎 ≈ QTextDocument/QTextLayout, 管换行/字体/富文本/选区。底层设施, 平时不直接碰
- **UITextView**: UIKit 的富文本编辑控件 ≈ QTextEdit, 底层就是 TextKit。功能最强 (跨节点选择/光标/长文编辑), 但 SwiftUI 里不能直接用
- **UIViewRepresentable**: SwiftUI ↔ UIKit 的桥 ≈ 在 QML 里嵌 QWidget 的那层桥。只有要用 UITextView 时才写它

按你第 7 条的 UI 形态, **TextKit / UITextView / UIViewRepresentable 这套可以先整个忘掉** —— 起步方案 (List + 每行自绘 + TextField) 全在 SwiftUI 原生范围内。

## 7. 苹果[待办]的智能分类列表怎么搭的

分两层:

- **数据层 (智能分类的实质)**: 不是特殊数据结构, 而是"保存的查询条件"。每条待办有字段 (标题/备注/到期日/旗标/所属列表), "今天""计划""旗标"这些智能列表 = 一组过滤谓词 (due=今天 / 有 due / flagged=true), 渲染时执行查询得到行数组
- **UI 层**: 一列行, 每行自定义: 前导圆圈 (复选框) + 标题 (可折行) + 次要行 (备注) + 尾部标签 chip, 按所属列表分区; 行高自适应, 内容折行就长高

苹果内部具体用什么框架不公开 (早年 Reminders 是 UIKit 写的, 近年苹果自家 app 在陆续迁 SwiftUI), 但这不影响我们 —— 这类列表用 SwiftUI 的 `List` 就能做出同样的东西。

映射到我们: 每行 = 缩进 + 圆点 (颜色按一级祖先、大小按级) + 文本段 (前缀/正文/尾缀可分别着色), 折行天然支持, 折叠 = 不渲染不可见节点, 点开 = 该行展开为多行编辑。比待办多出来的只有"树"和"折叠", 而折叠之后对列表控件来说依然是平铺行 —— 正落在 SwiftUI List 的能力正中。

附赠一句: 待办"智能分类"的思路以后也可以用到 dog 的框词/时间戳上 (按框词或日期聚合成智能视图), 那是后续功能, 不影响现在。

### 10.15 周四
1. TextField是纯文本, 不是富文本对吧, 不会被贴入html直接影响吧? 之前qt那个玩意直接被html影响样式, 还要单独处理. 然后, 为了定位光标固定样式啥的, 还被迫用了qt的那个玩意, 不能用qt的纯文本, 咱们在swift这里不用这么麻烦了对吧?





对, `TextField` 是纯文本, 而且这套麻烦在 Swift 这边**结构上就不存在**。拆开说:

## 为什么 HTML/样式进不来

1. **模型是 String**。`TextField` 绑定的类型就是 `String` —— 没有富文本文档模型, 样式无处存放。粘贴进来的内容只能变成一堆字符
2. **粘贴板只取纯文本表示**。iOS 粘贴板里一个条目可以同时携带多种表示 (带样式的、纯文本的), 而绑 String 的控件只会去取纯文本那一种 —— 带样式的那份根本不会被读取。你在 Qt 里遇到的 "HTML 直接改样式", 在 Swift 这边没有通路
3. **富文本是显式选择加入的**。新版 SwiftUI 的 TextEditor 确实支持富文本, 但那是绑 `AttributedString` 时才有的能力 —— 你不主动选, 就没有。绑 String 永远是纯文本

## Qt 为什么被迫, Swift 为什么不被迫

Qt 的问题出在架构: `QLineEdit` 是纯文本但能力弱 (光标/选择/布局都受限), 被迫上 `QTextEdit` —— 而 QTextEdit 的**文档模型就是 HTML**, "存储"和"编辑控件"绑死在一起, 所以粘贴内容天然携带样式, 你得单独洗。

Swift 这边是分开的两层:

|                      | 职责                             | 内容类型                                                     |
| -------------------- | -------------------------------- | ------------------------------------------------------------ |
| 展示层 (`Text`)      | 只读展示, 着色/圆点/前缀尾缀样式 | 样式由解析器每次现算, 是 `Text`/`AttributedString`, 单向渲染 |
| 编辑层 (`TextField`) | 输入                             | 只持有 `String`                                              |

**样式永远是你从解析结果现算出来的, 粘贴内容碰不到它**。Qt 那边是"样式存在控件里", Swift 这边是"样式每次从模型重算" —— 粘贴脏东西最多脏了字符串本身, 脏不了样式。

## 光标/选择也不用换控件

focus 有 `@FocusState`, 选择范围有 selection 绑定 (iOS 18+), 都是普通输入控件的正常 API —— 不需要"为了管光标去用富文本控件"。将来若真为了"跨节点自由选择"上 UITextView, 那动机是选择行为, 不是样式, 而且到时也可以让它全属性由你掌控。

## 真正要处理的类似问题 (内容层, 不是样式层)

粘贴多行文本、前导空白、特殊字符 —— 这些你的 dog 规格里已经有对策 (多行 → 包装块, 前导空白 → lstrip), 且都在**模型层一处收口**, 比在控件层洗 HTML 干净得多。顺带: `TextField(axis: .vertical)` 会**保留**粘贴进来的换行 (单行模式则会吞掉换行) —— 这正好是你"多行节点"想要的。

唯一要提前想的分叉: 如果"编辑态也要看到前缀/尾缀着色", 那才进入下一档 (AttributedString 编辑或 UITextView), 届时才需要处理"粘贴带属性"的问题 —— 有拦截点, 一处收口即可。**建议起步: 编辑态纯文本, 着色只做在展示态**, 最简单, 且绝对干净。
