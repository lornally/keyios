## 为什么要有 `some`：因为要**藏类型**

提案开篇说的就是要解决"**返回值层面的类型抽象**"（type-level abstraction for returns）。它的例子是一个图形库：

```swift
var shape: some Shape { ... }   // 我想说的只是"返回某个 Shape"
```

在这之前，你只有两条路，各有毛病：

**路 1：把具体类型写出来** —— `var shape: Union<Rectangle, Transformed<Rectangle>>`

- 又长又丑，读代码的人根本不需要知道
- 更要命的是**它把实现暴露给了调用方**：别人可能就依赖上你这个具体类型了，你以后想改实现（提案原话：换成 `NPointedStar`）就是破坏性改动。原话是这么说的：

  > Spelling out the return type also effectively reveals most of the implementation... making the declaration **brittle**

**路 2：用协议当类型（盒子 / 手写类型擦除）**

- 藏是藏住了，但提案原话：**comes with tradeoffs that are not always acceptable** —— 动态派发、运行时开销；而且调用方**拿不到"类型身份"**（关联类型就没了）

**`some` 是第三条路**，一句话总结它的定位：

> The underlying concrete type is **hidden**, and can even change from one version of the library to the next without breaking those clients... **Unlike an existential, though, clients still have access to the type identity.**

即：**对外藏起来（想换实现随时换），但对编译器不藏（不装箱、类型信息完整）。**

## 官方给的心智模型：反向泛型

提案里明确写了这么个类比（我觉得这是最贴切的解释）：

```swift
func 泛型版<T: Shape>() -> T      // 类型由【调用方】挑, 实现方被动
func 反向版() -> some Shape       // 类型由【实现方】挑, 调用方只看到"某个符合 Shape 的"
```

普通泛型：**调用方**决定用什么类型。`some`：**实现方**决定，然后把它藏起来给调用方。

## 为什么 SwiftUI 非用它不可

把上面的动机套进 `body`，三重压力正好汇到一起：

1. 具体类型**写不出来**（`WindowGroup<ModifiedContent<...>>` 嵌套几十层）
2. 具体类型**会变**（你改一行的布局，那个类型就变）—— 藏起来才不用每次改签名
3. 但 body **每秒跑几百次**，绝对不能是盒子（装箱 + 动态查找）

"藏起来 + 不变慢" = 正好只有 `some` 这一条路。

所以"为啥要 some"的完整答案是：**它不是修饰 `Scene` 的，它是 Swift 新造的一类类型 —— "被藏起来的具体类型"。** 出现的动机是封装（不让调用方依赖实现细节），性能是它相对盒子的优势，而 SwiftUI 那种"又长又会变、又必须快"的类型，是它最典型的用户。

**是"最绕"的一处，但不是唯一一处。** 按 Swift 6 的现状，语言概念上的复杂度可以排个序：

## 1. 泛型 / associatedtype / some-any：概念最绕

它绕在**同一个"占位类型"有四种写法，规则还不一样**：

| 写法             | 谁定            | 有盒子吗     |
| ---------------- | --------------- | ------------ |
| 具体类型 `青蛙`  | 你写死          | 无           |
| `<T>` / `some P` | 用的人 / 函数体 | 无（编译期） |
| `any P`          | 运行时那个值    | 有（见证表） |

再叠上这堆配套概念：主关联类型、开盒（opening existentials）、条件遵循、追溯遵循、same-type 约束、类型擦除（`AnyView`/`AnyHashable`）。

最能说明它绕的是这种"墙"（实测）：

```swift
let ys: [any 容器] = [箱(), 箱()]
func 收集<T: 容器>(_ xs: [T]) {}
收集(ys)   // ❌ type 'any 容器' cannot conform to '容器'
```

明明 `any 容器` 里装的都遵循了 `容器`，却递不进泛型函数——两个"容器"不是一回事。`any` 关键字、主关联类型，本质上都是在给这块打补丁。

## 2. 并发隔离（Swift 6）：现在**实际耗时最多**的其实是它

`Sendable` / actor / `@MainActor` / `nonisolated` / 区域隔离。同一段代码：

```swift
final class 计数器 { var n = 0 }
func 收(_ f: @Sendable @escaping () -> Void) {}
func 试() { let c = 计数器(); 收 { print(c.n) } }
```

- Swift 5 模式：**一声不吭**（-typecheck 和真编都不报）
- Swift 6 模式：`capture of 'c' with non-Sendable type '计数器' in a '@Sendable' closure`

迁移时成片的这种错、且错误信息不直白；SwiftUI 整个 UI 又都在 `@MainActor`，跟后台任务交界的地方很容易踩。对写 app 的人来说，这块比泛型更磨人。

## 3. 剩下几块

- **SwiftUI 的元语言**：property wrapper（`@State`/`@Binding`/`@Environment`）、result builder（`@ViewBuilder`）、值语义 + 刷新规则。"为什么改了不刷新"都出在这一层。
- **内存**：ARC + `weak`/`unowned` 破环；新加的 `~Copyable`、`consuming`/`borrowing` 又把所有权那套引进来。
- **互操作**：ObjC/C 桥接、`@objc`、内存布局 —— 库作者才碰。

反过来说，**看起来吓人其实简单**的：可选、`enum` + switch、值/引用、闭包语法 —— 学一次就懂，不会反复撞墙。

## 为什么偏偏泛型这块绕

事实层面：Swift 需要同时满足几个互相拉扯的目标——静态特化（值类型要快）、运行时擦除（异质容器）、C/ObjC 互操作、ABI 稳定、源码兼容。每加一个目标就多一套写法。Rust 用 `impl Trait` / `dyn Trait` 表达同样的两分，Haskell 用 type class + existential —— **"参数化多态 + 存在类型"这件事本身在哪个语言里都不轻**，不是 Swift 独有的。

一句话：**问"最抽象、最容易反复踩坑"，答案就是 associatedtype/泛型/some-any 这一窝；问"实际最耗时"，现在是并发隔离。**
